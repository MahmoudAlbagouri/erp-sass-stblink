# بحوث العمليات (Operations Research) — جاهزية البيانات

النظام اليوم **يسجّل**، وغداً سيقترح بنفسه: كم تشتري ومتى، من أي فرع تحوّل،
كم موظفاً تحتاج كل ساعة، أي طيار يأخذ أي أوردر، وأي عرض يستحق التكرار. كل
اقتراح من هذه مسألة بحوث عمليات تحتاج **تاريخاً** من البيانات، وما لم يُسجَّل لحظة
حدوثه لا يُسترجع بعدها.

هذا الملف هو المرجع لذلك: القاعدة التي تحكم كل ميزة جديدة، وخريطة ما يُسجَّل
الآن وأين، وما ينقص، وترتيب البناء.

## القاعدة

**سجّل التاريخ الذي لا يُسترجع، وأجّل المعاملات.**

| النوع | مثال | متى يُبنى |
|---|---|---|
| **حدث تاريخي**: وقع مرة ولن يتكرر | سبب تلف بضاعة، تاريخ طلب من مورد، موقع عميل، عرض طُبّق على بيعة، وقت بدء تحضير طبق | **الآن**، مع الميزة نفسها |
| **معامل** (parameter): رقم يضبطه المستخدم | تكلفة الطلبية، نسبة تكلفة التخزين، مستوى الخدمة المطلوب | **مع الخوارزمية** التي تستعمله — تأجيله لا يضيّع شيئاً |
| **ناتج**: ما تحسبه الخوارزمية | حد إعادة الطلب المقترح، كمية الطلب، جدول الوردية | لا يُخزَّن مدخلاً أبداً: يُحسب ويُعرض اقتراحاً |

حقل تاريخي جديد يكون **اختيارياً** (nullable)، ولا يغيّر سلوكاً قائماً، ولا يُرفض
به مستند وقع فعلاً (بيع كاشير طُبع بلا إنترنت يُهمل الحقل الخاطئ ولا يُرفض).

### قائمة فحص لأي ميزة جديدة

قبل إغلاق أي ميزة (في موديول قائم أو جديد كالمصانع والمطاعم):

1. **الوقت**: هل لكل حدث مهم وقته الفعلي؟ (`occurredAt` لا وقت الرفع؛ بداية
   ونهاية لكل مرحلة: طُلب، بدأ، انتهى، سُلِّم.)
2. **السبب**: حين ينقص شيء أو يُرفض أو يُلغى — هل يُسجَّل لماذا (قائمة أسباب
   ثابتة، لا نص حر وحده)؟
3. **الكمية المخططة مقابل الفعلية**: طُلب 100 ووصل 95؟ خُطط 50 وأُنتج 48؟
   الاثنان يُحفظان، لا الأخير وحده.
4. **التكلفة وقت الحدث**: تُنسخ على السطر (كما `unitCost` على الحركات)، لا تُقرأ
   لاحقاً من سعر تغيّر.
5. **المكان**: فرع / مخزن / مركز عمل / طاولة / موقع على الخريطة.
6. **من**: الموظف أو الجهاز أو الطيار الذي نفّذ (لقياس الطاقة والإنتاجية).
7. **الطاقة**: ما حدّ المورد؟ (مقاعد الطاولة، ساعات الماكينة، سعة الطيار.)
8. **لا تكسر شيئاً**: الحقل اختياري، والأجهزة القديمة تعمل بدونه، وفي الويب
   والتطبيق معاً إن كان للشاشة نسختان.

ثم سجّل ما أضفته في [الخريطة](#خريطة-البيانات) أدناه.

## خريطة البيانات

ما يُسجَّل الآن، ولأي مسألة.

### الطلب والمخزون

| المسألة | المصدر | ملاحظات |
|---|---|---|
| **توقّع الطلب** (forecasting) لكل صنف × مخزن × يوم | `stock_movements` بنوع `sale` و`sale_return`، بوقت `occurredAt` | الدفتر لا يُعدَّل، والبيع الأوفلاين يحتفظ بوقته الأصلي |
| الطلب بالساعة (للعمالة والمطبخ) | `sales_invoices.issuedAt` + `sales_invoice_lines` | الوقت الفعلي على الجهاز |
| **أيام النفاد** (الطلب المخفي) | `stock_movements.balanceAfter` ≤ 0 بين حركتين | يوم بلا بيع والرصيد صفر ≠ يوم بلا طلب: يُستبعد من التوقّع |
| حد إعادة الطلب الحالي | `stock_levels.minQuantity` | يدوي اليوم؛ سيُقترح |
| التكلفة | `inventory_items.avgCost` / `lastCost`، و`unitCost` على كل حركة وسطر | منسوخة وقت الحدث |
| تاريخ أسعار الشراء لكل مورد | `purchase_invoice_lines.unitCost` + `purchase_invoices.supplierId`/`invoiceDate` | |
| **مدة التوريد** | `suppliers.leadTimeDays` (المعتادة) و`purchase_invoices.orderDate` → `invoiceDate` (الفعلية لكل طلب) | أُضيفا 2026-11 |
| مدة التحويل بين المخازن، والعجز فيه | `stock_transfers.sentAt` → `receivedAt`، و`stock_transfer_lines.quantity` مقابل `receivedQuantity` | |
| **الهالك والفاقد** | `stock_movements.reason` (`StockAdjustmentReason`) للتسويات؛ فروق الجرد بنوع `stocktake` | السبب أُضيف 2026-11 |
| مواقع المخازن | `warehouses.branchId` → `branches.latitude`/`longitude` | |
| **الصلاحية والتلف** (FEFO، تقدير الفاقد بالانتهاء) | `stock_lots.expiryDate` / `manufactureDate` / `supplierId`، `stock_lot_levels`، `stock_movement_lots` (أي دفعة خرجت في أي حركة) | أُضيفت 2026-11 مع المصانع |

## الفجوات المعروفة

ما لا يُسجَّل بعد، ولماذا لم يُضف الآن:

| الفجوة | لماذا تهم | لماذا لم تُضف |
|---|---|---|
| **المبيعات الضائعة**: عميل طلب صنفاً نافداً | الطلب الحقيقي أكبر مما بيع | تحتاج زراً في شاشة الكاشير ("غير متوفر") — ميزة لا حقل |
| **أمر الشراء** والكمية المطلوبة مقابل المستلمة | نسبة تلبية المورد (fill rate) | المسودة تُعدَّل إلى الفاتورة فتضيع الكمية الأولى؛ تحتاج كيان أمر شراء |
| **وقت كل طبق** داخل المحطة | جدولة دقيقة للمطبخ | المحطة تُسجَّل لكل بون (كافٍ للاختناق)؛ الطبق الواحد يحتاج شاشة مطبخ تضغط لكل سطر |
| **سلسلة التوريد للتصنيع**: أمر الشراء المفتوح وتاريخ وصوله المتوقع | MRP بتواريخ أدق | مسودات الشراء تُحسب "قادماً" بلا تاريخ وصول — يُبنى مع كيان أمر الشراء |
| الجدولة التفصيلية للأوامر على المراكز (أي أمر قبل أي) | جدولة الإنتاج (Job-shop) | البيانات كاملة (الطاقة، الأوقات القياسية والفعلية)؛ الخوارزمية نفسها مرحلة 3 |
| تكلفة الطلبية، نسبة التخزين، مستوى الخدمة | معادلات المخزون | معاملات: تُبنى مع الخوارزمية (القاعدة) |
| **قراءات حساسات المزرعة** (رطوبة التربة، عداد البئر) | ري بالطلب لا بالموعد | تحتاج تكامل أجهزة (IoT) — المياه تُسجَّل اليوم يدوياً بكميتها ومدتها |
| **صور الإصابة** في الفحص الميداني | تشخيص أدق وتدريب نماذج | رفع الملفات لا يعمل بلا إنترنت؛ تُضاف حين يُبنى طابور ملفات |

## ترتيب البناء

بعد الموديولات الكبيرة (المصانع والمطاعم وغيرها):

| المرحلة | المحتوى | يعتمد على |
|---|---|---|
| 0 — الأساس | جدول الطلب اليومي لكل صنف × مخزن مستبعداً أيام النفاد، تصنيف ABC/XYZ، إعدادات الشركة (تكلفة الطلبية، نسبة التخزين، مستوى الخدمة) | الخريطة أعلاه |
| 1 — اقتراح الشراء | توقّع الطلب، المخزون الآمن، حد إعادة الطلب، الكمية الاقتصادية (EOQ)، شاشة اقتراحات مجمّعة بالمورد تتحول لمسودة فاتورة شراء | مدة التوريد |
| 2 — موازنة الفروع | برمجة خطية تقترح تحويلات بين المخازن قبل الشراء | مواقع المخازن ومدة التحويل |
| 3 — حسب الموديول | المصانع: MRP وجدولة الإنتاج. المطاعم: احتياج الخامات من المنيو، كمية التحضير، العمالة بالساعة. التوصيل: إسناد الطيارين والمسارات. المزارع: التنبؤ بالإنتاج، جدولة الري بطاقة الآبار، توزيع فرق العمل على الوحدات، والإنذار المبكر للآفات | بيانات كل موديول |

### أين ستعمل الحسابات

- **دفعة ليلية** بـ `@Cron` (الجدولة مسجّلة مرة واحدة في AppModule) لكل شركة،
  تكتب نتائجها في جدول توصيات؛ لا حساب ثقيل وقت الطلب.
- **السيرفر عملية واحدة** (PM2 fork): الحساب الثقيل في `worker_threads` أو بعد
  منتصف الليل بتوقيت الشركة، فلا يتعطل الكاشير.
- **بلا حلّال** للمرحلتين 0 و1 (معادلات + Exponential Smoothing بـ `decimal.js`).
  **HiGHS** (WASM داخل Node) للبرمجة الخطية في المرحلة 2. خدمة منفصلة
  (Python + OR-Tools) فقط لمسائل الجدولة والمسارات (CP-SAT / VRP).
- **الموسمية**: رمضان والعيد يتحركان مع التقويم الهجري (~11 يوماً كل سنة
  ميلادية) فيُعاملان كأحداث في التقويم لا كموسم ثابت؛ وأول الشهر (الرواتب) نمط
  أسبوعي/شهري.
- **شركة جديدة** بلا ثلاثة أشهر من البيع: تبقى على `minQuantity` اليدوي حتى
  تكفي البيانات.
